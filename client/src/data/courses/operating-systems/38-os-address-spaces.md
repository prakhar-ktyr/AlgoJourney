# Logical vs Physical Addresses

Understanding the distinction between **logical** (virtual) and **physical** addresses is fundamental to modern memory management. This separation is what makes virtual memory, process isolation, and dynamic relocation possible. In this lesson, we explore how the CPU generates addresses, how hardware translates them, and why this abstraction is essential.

---

## Two Worlds of Addresses

Every running program generates memory references — loading variables, jumping to functions, pushing data onto the stack. But where do these addresses point? That depends on the **address space** being used.

> **Logical address** (also called _virtual address_): An address generated by the CPU during program execution. This is what the program "sees."

> **Physical address**: The actual address of a location in the physical memory hardware (RAM). This is what the memory bus and DRAM chips use.

| Property                   | Logical Address                     | Physical Address                     |
| -------------------------- | ----------------------------------- | ------------------------------------ |
| **Generated by**           | CPU (program instructions)          | Memory Management Unit (MMU)         |
| **Visible to**             | User program                        | Memory hardware                      |
| **Range**                  | Logical address space (per process) | Physical address space (system-wide) |
| **Also called**            | Virtual address                     | Real address, hardware address       |
| **Can change at runtime?** | No (fixed within program)           | Yes (if process is relocated)        |

---

## When Logical Equals Physical

Under **compile-time** and **load-time** binding, the addresses generated by the program are the same as the physical addresses. No translation is needed.

### Compile-Time Binding

```text
  Source code → Compiler → Absolute addresses → Memory

  Program compiled for address 0x1000:

  Logical address 0x1000 = Physical address 0x1000
  Logical address 0x1004 = Physical address 0x1004
  ...

  No translation. But program CANNOT be moved to a different location.
```

### Load-Time Binding

```text
  Source code → Compiler → Relocatable code → Loader adjusts → Memory

  If loaded at base address 0x5000:

  Logical offset 0x0000 → Physical address 0x5000
  Logical offset 0x0100 → Physical address 0x5100

  Addresses fixed at load time. Process cannot move after loading.
```

> [!NOTE]
> In both compile-time and load-time binding, logical and physical addresses are identical (or deterministically related). This works but is inflexible — the process cannot be moved in memory after loading without reloading.

---

## When Logical ≠ Physical: Execution-Time Binding

Modern operating systems use **execution-time** (runtime) binding. The logical address generated by the CPU is different from the physical address used to access memory. A hardware device translates between them **on every memory access**.

```text
  Program                     Hardware                    Memory
  generates                   translates                  stores
  ┌───────────┐    logical    ┌──────────┐   physical    ┌──────────┐
  │   CPU     │───address────→│   MMU    │───address────→│   RAM    │
  │           │    (346)      │          │    (14346)    │          │
  └───────────┘               └──────────┘               └──────────┘
                              Relocation
                              register = 14000

                              Physical = Logical + Relocation
                              14346   = 346    + 14000
```

This means:

- The user program **never** sees or uses physical addresses.
- The program works with logical addresses in the range $[0, \text{max}]$.
- The MMU transparently maps each logical address to a physical address.

---

## The Memory Management Unit (MMU)

The **MMU** is a hardware device (integrated into the CPU in modern processors) that performs address translation at full CPU speed.

### Basic MMU: Relocation Register Scheme

The simplest MMU uses a single **relocation register** (also called the **base register**):

$$\text{Physical Address} = \text{Relocation Register} + \text{Logical Address}$$

```text
  ┌────────────────────────────────────────────────────────┐
  │                        CPU                              │
  │                                                         │
  │  ┌──────────┐          ┌─────────────────────┐         │
  │  │ Program  │          │       MMU           │         │
  │  │ Counter  │ logical  │ ┌─────────────────┐ │ physical│
  │  │          │──addr───→│ │ Relocation Reg  │ │──addr──→ Memory
  │  │ (346)    │          │ │    (14000)      │ │ (14346) │
  │  └──────────┘          │ │                 │ │         │
  │                         │ │ 346 + 14000    │ │         │
  │                         │ │ = 14346        │ │         │
  │                         │ └─────────────────┘ │         │
  │                         └─────────────────────┘         │
  └────────────────────────────────────────────────────────┘
```

### Key Properties

| Property         | Description                                                                                                                 |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **Transparency** | The user program is completely unaware of the relocation. It uses addresses 0, 1, 2, ... as if it has memory all to itself. |
| **Speed**        | Translation happens in hardware, adding essentially zero overhead to each memory access.                                    |
| **Flexibility**  | The OS can move a process in memory by simply updating the relocation register.                                             |
| **Protection**   | Combined with a limit register, prevents access to other processes' memory.                                                 |

---

## Address Space

> **Logical address space**: The set of all logical addresses generated by a program. For a process with addresses 0 through $\text{max}$, the logical address space is $[0, \text{max}]$.

> **Physical address space**: The set of all physical addresses corresponding to the logical address space. Determined by the MMU mapping.

```text
  Logical Address Space         Physical Address Space
  (per process)                 (system-wide)

  ┌────────────────┐            ┌────────────────────────┐
  │ 0x0000: code   │            │ 0x0000: OS kernel      │
  │ 0x1000: data   │  ──MMU──→  │ ...                    │
  │ 0x2000: heap   │            │ 0x14000: P1's code     │
  │ 0x3000: stack  │            │ 0x15000: P1's data     │
  └────────────────┘            │ 0x16000: P1's heap     │
                                │ 0x17000: P1's stack    │
  Process P1 thinks it          │ ...                    │
  starts at address 0.          │ 0x28000: P2's code     │
                                │ ...                    │
  Process P2 also thinks        └────────────────────────┘
  it starts at address 0!
  (Different relocation register)
```

> [!IMPORTANT]
> Every process believes it has the entire address space to itself, starting from address 0. The MMU ensures that different processes' logical address 0 maps to different physical addresses. This is the foundation of **process isolation**.

## Protection with Base-Limit Registers

The relocation register alone handles translation but not protection. Adding a **limit register** provides both:

```text
  ┌──────────────────────────────────────────────────────┐
  │                      CPU                              │
  │                                                       │
  │  Logical    ┌─────────────────────────────────┐      │
  │  Address ──→│ Is address < limit register?     │      │
  │  (addr)     │                                  │      │
  │             │  YES                    NO       │      │
  │             │   │                     │        │      │
  │             │   ↓                     ↓        │      │
  │             │ ┌──────────────┐   ┌──────────┐ │      │
  │             │ │ Add base     │   │ TRAP:    │ │      │
  │             │ │ register     │   │ Address  │ │      │
  │             │ │              │   │ Error    │ │      │
  │             │ │ physical =   │   │ (segfault│ │      │
  │             │ │ base + addr  │   │  to OS)  │ │      │
  │             │ └──────┬───────┘   └──────────┘ │      │
  │             └────────┼────────────────────────┘      │
  │                      │                                │
  │                      ↓                                │
  │                   Memory                              │
  └──────────────────────────────────────────────────────┘
```

### Address Validation Flow

| Step | Action                               | Result                                                      |
| ---- | ------------------------------------ | ----------------------------------------------------------- |
| 1    | CPU generates logical address `addr` | Address enters MMU                                          |
| 2    | Compare: `addr < limit`?             | Check bounds                                                |
| 3a   | If yes: `physical = base + addr`     | Valid access → memory                                       |
| 3b   | If no: generate trap                 | Addressing error → OS handles (typically kills the process) |

### Worked Example

```text
  Process P1: base = 20000, limit = 5000

  Logical address 0     → Physical 20000 (valid: 0 < 5000)
  Logical address 3000  → Physical 23000 (valid: 3000 < 5000)
  Logical address 4999  → Physical 24999 (valid: 4999 < 5000)
  Logical address 5000  → TRAP! (invalid: 5000 ≮ 5000)
  Logical address 7000  → TRAP! (invalid: 7000 ≮ 5000)
```

## Context Switching and Address Spaces

When the OS switches between processes, it must update the relocation and limit registers:

```text
  Context Switch: P1 → P2

  ┌──────────────────────────────────────────────┐
  │ 1. Save P1's state (registers, PC, etc.)     │
  │ 2. Load P2's state                            │
  │ 3. Set base register = P2's base address     │
  │ 4. Set limit register = P2's memory size     │
  │ 5. Resume P2                                  │
  └──────────────────────────────────────────────┘

  P1: base=20000, limit=5000  →  P2: base=30000, limit=8000

  Same logical address 100 now maps to:
  - Physical 20100 when P1 runs
  - Physical 30100 when P2 runs
```

This register update is part of the context switch overhead, but it is very fast (writing two registers).

## The User's Perspective

The user program operates in a clean, simple world:

```text
  User Program's View:              Reality (Physical Memory):

  ┌────────────────────┐            ┌──────────────────────────┐
  │ 0x0000: main()     │            │ 0x00000: OS Kernel       │
  │ 0x0100: foo()      │            │ ...                      │
  │ 0x0200: data       │            │ 0x50000: P1 main()       │
  │ 0x0300: heap       │            │ 0x50100: P1 foo()        │
  │ ...                │            │ 0x50200: P1 data         │
  │ 0xFFFF: stack      │            │ ...                      │
  └────────────────────┘            │ 0x80000: P2 main()       │
                                    │ ...                      │
  "I have memory from              └──────────────────────────┘
   0 to 0xFFFF, all mine!"
                                    Multiple processes coexist
                                    in physical memory.
```

| What the program sees              | What actually happens                    |
| ---------------------------------- | ---------------------------------------- |
| Linear address space starting at 0 | Mapped to arbitrary physical addresses   |
| Contiguous memory                  | May be non-contiguous (with paging)      |
| Full ownership of address space    | Shared physical memory, protected by MMU |
| No other processes visible         | Other processes exist but are invisible  |

## Address Translation in Different Schemes

As memory management techniques evolved, the MMU became more sophisticated:

| Scheme                 | Translation Method              | Granularity                   |
| ---------------------- | ------------------------------- | ----------------------------- |
| **Base + Limit**       | Physical = base + logical       | Whole process                 |
| **Paging**             | Page table lookup: page → frame | Fixed-size pages (e.g., 4 KB) |
| **Segmentation**       | Segment table: base + offset    | Variable-size segments        |
| **Segmented Paging**   | Segment → page table → frame    | Two-level                     |
| **Multi-level Paging** | Hierarchical page table walk    | Pages, with table hierarchy   |

We will explore paging, segmentation, and their combinations in upcoming lessons.

## C Demonstration: Observing Logical vs Physical Addresses

```c
#include <stdio.h>
#include <unistd.h>

int global_var = 42;

int main() {
    int local_var = 100;
    int *heap_var = malloc(sizeof(int));
    *heap_var = 200;

    printf("PID: %d\n", getpid());
    printf("Address of global_var: %p (logical)\n", &global_var);
    printf("Address of local_var:  %p (logical)\n", &local_var);
    printf("Address of heap_var:   %p (logical)\n", heap_var);
    printf("\nThese are LOGICAL addresses.\n");
    printf("The physical addresses are different\n");
    printf("and managed by the MMU.\n");

    free(heap_var);
    return 0;
}
```

**Sample output:**

```text
PID: 12345
Address of global_var: 0x404028 (logical)
Address of local_var:  0x7ffd3a2b1c4c (logical)
Address of heap_var:   0x55a3b8e012a0 (logical)

These are LOGICAL addresses.
The physical addresses are different
and managed by the MMU.
```

> [!TIP]
> If you run two instances of this program, they will print the **same** logical addresses for `global_var` (because each has its own virtual address space), but the physical addresses will be different. You can check physical addresses on Linux using `/proc/<pid>/pagemap`.

## Python Demonstration: Address Spaces

```python
import os

x = 42
y = [1, 2, 3]

print(f"PID: {os.getpid()}")
print(f"Address of x: {hex(id(x))}")
print(f"Address of y: {hex(id(y))}")
print()
print("These are logical (virtual) addresses.")
print("The OS and MMU map them to physical RAM addresses.")
print("Each process gets its own isolated address space.")
```

## Why This Matters: Benefits of Logical-Physical Separation

| Benefit                    | Explanation                                                                           |
| -------------------------- | ------------------------------------------------------------------------------------- |
| **Process isolation**      | Each process has its own address space; cannot corrupt others                         |
| **Relocation**             | Process can be loaded at any physical address; OS decides at runtime                  |
| **Virtual memory**         | Logical address space can be larger than physical memory                              |
| **Sharing**                | Same physical frames can appear in multiple logical address spaces (shared libraries) |
| **Protection**             | Hardware enforces boundaries; software bugs cause segfaults, not system crashes       |
| **Simplified programming** | Programmer doesn't need to know physical memory layout                                |

## Historical Context

| Era       | Address Scheme            | Limitation                                    |
| --------- | ------------------------- | --------------------------------------------- |
| 1950s-60s | Absolute addresses        | One process at a time; no relocation          |
| 1960s     | Base + limit registers    | Simple relocation; limited flexibility        |
| 1970s     | Segmentation              | User-visible segments; external fragmentation |
| 1980s     | Paging                    | Fixed-size pages; no external fragmentation   |
| 1990s+    | Multi-level paging + TLB  | Efficient for large address spaces            |
| 2000s+    | 64-bit virtual addressing | $2^{64}$ byte address spaces (16 exabytes!)   |

## Try It Yourself

**Exercise 1:** A system uses a relocation register scheme. Process A has base = 10000 and limit = 4000. Process B has base = 25000 and limit = 6000. Translate these logical addresses:

- Process A: logical 0, 2000, 3999, 4000
- Process B: logical 0, 5999, 6000

:::details Solution
**Process A** (base=10000, limit=4000):
| Logical | < limit (4000)? | Physical (base + logical) | Valid? |
|---------|----------------|--------------------------|--------|
| 0 | 0 < 4000 ✓ | 10000 + 0 = 10000 | ✓ |
| 2000 | 2000 < 4000 ✓ | 10000 + 2000 = 12000 | ✓ |
| 3999 | 3999 < 4000 ✓ | 10000 + 3999 = 13999 | ✓ |
| 4000 | 4000 < 4000 ✗ | TRAP | ✗ (boundary violation) |

**Process B** (base=25000, limit=6000):
| Logical | < limit (6000)? | Physical | Valid? |
|---------|----------------|----------|--------|
| 0 | 0 < 6000 ✓ | 25000 | ✓ |
| 5999 | 5999 < 6000 ✓ | 30999 | ✓ |
| 6000 | 6000 < 6000 ✗ | TRAP | ✗ |
:::

**Exercise 2:** Two processes run the same compiled program. Both have a variable `count` at logical address 0x1000. Explain how both can coexist in physical memory without conflicts.

:::details Solution
Each process has its own **relocation register** value:

- Process A: relocation register = 50000. `count` at physical address 50000 + 0x1000 = 54096.
- Process B: relocation register = 80000. `count` at physical address 80000 + 0x1000 = 84096.

Even though both use the same logical address (0x1000), they map to **different physical addresses** (54096 and 84096). The MMU performs the translation transparently. When the OS context-switches from A to B, it changes the relocation register value, so the same logical address now points to B's physical memory.

This is why each process appears to have its own private memory — the address space abstraction.
:::

## Key Takeaways

- **Logical addresses** are generated by the CPU/program; **physical addresses** are the actual RAM locations.
- With **compile-time** and **load-time** binding, logical = physical. With **execution-time** binding, they differ.
- The **Memory Management Unit (MMU)** is a hardware device that translates logical → physical addresses at CPU speed.
- The simplest MMU uses a **relocation register**: $\text{physical} = \text{base} + \text{logical}$.
- **Base + limit registers** provide both relocation and protection — the limit register prevents out-of-bounds access.
- Every process sees its own **logical address space** starting at 0, completely unaware of physical layout.
- The user program **never** sees or uses physical addresses — the abstraction is enforced by hardware.
- This separation enables **process isolation**, **relocation**, **virtual memory**, and **memory sharing**.
- More sophisticated translation schemes (paging, segmentation) build on this same logical-physical separation.
